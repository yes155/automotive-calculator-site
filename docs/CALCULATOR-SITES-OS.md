# Calculator Sites OS

## 1. Project boundary

A niche site is the project boundary. Individual calculators are pages/tools inside that project.

Create a separate site only when the audience, monetization model, data model, brand, or topical graph is materially different.

## 2. Page-type separation

Keep these page types visibly and semantically distinct:

### Calculator / estimator
Answers: "What is my result?"

Core elements:
- input controls;
- unit choices where relevant;
- result;
- transparent formula/method;
- assumptions;
- worked example;
- interpretation;
- limitations;
- related tools.

### Cost guide
Answers: "What does X usually cost?"

Core elements:
- ranges;
- cost drivers;
- regional/context differences;
- scenarios;
- explanatory tables;
- related estimator CTA.

A guide may embed or link to an estimator, but the two intents must not be confused.

### Supporting guide
Explains a concept needed to use calculators correctly.

## 3. Keyword-to-URL rule

Do not create multiple URLs for keyword variants that solve the same task.

Merge synonyms and close variants when:
- SERP intent is substantially the same;
- required inputs are the same;
- result type is the same.

Split when:
- users need different inputs;
- output is materially different;
- task stage differs;
- SERPs show clearly different intent.

## 4. Launch sequencing

Prefer:
1. low/moderate-KD calculators with independent task value;
2. commercially useful calculators;
3. supporting calculators that create internal-link depth;
4. harder head terms after topical authority grows.

Do not launch only with the biggest head keyword.

## 5. Calculator UX standard

Each tool should have:
- useful default state without misleading prefilled results;
- labels with units;
- unit conversion where users reasonably expect it;
- inline validation;
- clear Calculate/Reset behavior;
- mobile-friendly controls;
- shareable/copyable result where useful;
- formula/method explanation;
- assumptions and edge cases;
- worked example;
- related calculators;
- accessible keyboard behavior.

## 6. SEO/GEO standard

Every important calculator page should expose:
- concise definition/answer near the top;
- calculator immediately accessible;
- explicit formula or methodology;
- variable definitions;
- assumptions;
- worked example;
- FAQ only when it adds distinct questions;
- source/methodology section;
- descriptive internal links;
- stable canonical URL;
- relevant structured data without unsupported claims.

Write so answer engines can extract:
- what the tool does;
- what inputs mean;
- how the calculation works;
- what the result means;
- when the result should not be treated as authoritative.

## 7. Trust and risk

Technical, electrical, structural, financial, health, or regulated calculations need stronger source review and limitations.

Do not present an approximate calculator as a substitute for:
- code compliance;
- licensed engineering;
- medical care;
- legal advice;
- tax advice;
- official manufacturer specifications.

## 8. Pre-launch QA

Before launch verify:
- every approved URL exists;
- no duplicate/cannibalizing URL variants;
- formulas pass test cases;
- units and conversions pass test cases;
- titles/H1s are not truncated;
- no missing images/assets;
- no broken internal links;
- mobile layout works;
- light/dark modes remain readable if dark mode exists;
- schema validates;
- canonical/robots/sitemap are correct;
- analytics is installed only where intended;
- no placeholder copy remains.
